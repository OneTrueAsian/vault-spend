# Mobile snapshot viewer

Tasks 3–7 provide a browser-only, read-only React viewer, encrypted offline repository and approved local refresh. The production entry opens saved copies from IndexedDB; a new device pairs through the desktop-approved HTTPS flow. `MobileViewer` receives ingress-validated snapshots.

From the repository root:

- `npm run mobile:dev` then open `http://127.0.0.1:1425/mobile/preview.html` for synthetic data, or `/mobile/index.html` for the production entry.
- `npm run mobile:build` writes only production assets to `dist-mobile`.
- `npm run mobile:build:preview` writes the separately labeled synthetic preview to `dist-mobile-preview`.
- `npm run mobile:preview` serves that built preview; open `/mobile/preview.html`.
- `npm run mobile:e2e` builds both entries and validates them in ordinary headless Edge. Requires the existing matching `~/.cargo/bin/msedgedriver.exe` (or `MSEDGEDRIVER` override). Screenshots go to the OS temporary directory unless `VAULTSPEND_MOBILE_TEST_OUTPUT` names another output directory.

- `npm run mobile:offline:e2e` builds a separate test-only entry in `dist-mobile-test` and exercises native IndexedDB, WebCrypto and service workers, including a cold Edge process restart with the local server stopped. Synthetic snapshots are injected by the test runner, never bundled with production. Private-storage/quota failures are injected; this is not physical-phone or private-browser acceptance.

The build rejects Tauri dependencies, production fixture imports and the test-only storage probe. Fonts, CSS and icons are bundled locally. Appearance choices are stored in localStorage. The repository saves each profile as AES-256-GCM ciphertext with a persisted, non-extractable CryptoKey and authenticated identity/version/ordering metadata. Financial plaintext and calculator inputs remain in memory. Profile/epoch/sequence replacement resets financial pages and scenario state; Settings stays open during pairing or refresh.

The mobile Settings tab contains appearance choices, pairing/removal/Forget controls, detailed connection status and saved-snapshot timestamps/Refresh. Profile switching and a compact saved-date/offline indicator remain above the financial pages. Pairing QR links open Settings directly.

Once loaded, navigation and calculators work without network access. The Task 4 native Edge probe verifies encrypted persistence, service workers and cold offline reopening. Remembered authorization and desktop refresh are implemented. The owner confirmed iPhone 16 Pro / Google Chrome pairing and functionality, with all saved data loading in airplane mode and Wi-Fi off. Exact versions, tab versus home-screen mode, Android and the broader physical acceptance matrix remain unconfirmed. Desktop browser checks do not replace phone acceptance.


## Desktop HTTPS foundation (Task 5)

`npm run build` builds both desktop and production mobile assets. The Tauri build script embeds the allowlisted mobile HTML, JS, CSS, fonts, manifest, worker and PNG icons into the executable. Run this build before Cargo checks in a fresh checkout; direct Cargo builds report a missing production mobile build. `tauri dev` builds mobile assets before starting the desktop dev server. No runtime Python/OpenSSL executable, Node server, directory serving or CDN is used by mobile delivery.

The Rust service is off by default. Its nonfinancial `mobile-network.json` is beside the installation's config, independent of profile databases. An explicit private IPv4 address, exact interface and fixed port are required; public/wildcard/loopback production bindings are rejected. Interface loss stops the listener. Desktop Quit stops it, tray behavior is preserved, and Windows suspend/resume uses the existing session hook. Certificate keys are protected by current-user DPAPI on Windows; the macOS adapter uses the OS Keychain and remains unverified on this Windows machine. Protection failures have no plaintext fallback.

The unique local root has ten-year validity; its 90-day server leaf has exactly the selected IP SAN and server-auth usage, and renews with 14 days remaining under that same root. Address changes and near-expired roots require explicit setup/trust reset; the server does not silently generate replacement trust. A persisted identity-created marker and configuration flag also reject missing keys after setup, including public-certificate export; restoring the original protected bundle preserves its identity. A new IP or port creates a new browser origin, so phone storage does not move automatically. Public root PEM/fingerprint export and network/status/enable/disable operations exist as desktop-only typed IPC commands; Settings UX and certificate instructions are implemented in Task 7; Task 6 adds the narrow authorized API described below. There is no HTTP command bridge.

Public delivery serves only embedded assets with exact Host/Origin checks and a restrictive CSP; Task 6 adds the authorized API below. Unknown/private-file paths return no-store errors, and writes/body-bearing requests are rejected. It limits simultaneous connections to 32, TLS and header preparation to five seconds each, and each connection to twenty seconds. Stopping it cancels outstanding handshakes/connections.

Compiled-app spec `feature166_mobile_https_assets.mjs` uses a disposable directory and a debug-only loopback fixture. Its Node TLS client trusts only that fixture's public root and keeps certificate/hostname validation enabled; no machine trust certificate or firewall change is made. The fixture and Quit probe are excluded from release registrations. Physical phone certificate trust, all browser modes, stable origin selection, actual NIC changes and macOS packaging remain acceptance requirements. The Task 5 listener alone does not establish a ready phone setup; Task 7 adds the application flow below.

## Pairing and authorized reads (Task 6)

The desktop can create a five-minute, single-use high-entropy pairing code. Redemption creates a pending request; it grants no access. The shared desktop confirmation dialog shows the phone-supplied label and requires explicitly selected profiles. Approval then permits a one-time claim completion over HTTPS. Code/claim state is memory-only, bounded and canceled on listener stop; attempts are rate limited. The protected device registry stores credential verifiers, opaque profile aliases and sequence/epoch metadata, without financial snapshots or raw credentials.

Remembered access uses a Secure/HttpOnly/SameSite=Strict host-only cookie, with expiry up to one year away, renewed on authenticated status/snapshot reads, with protected last-connection and expiry writes coalesced to five-minute intervals. The typed routes are `/api/pair/redeem`, `/api/pair/complete`, `/api/status`, `/api/snapshot/{opaque-profile-id}` and `/api/logout`. Requests require the exact Host, a same-origin custom header and no URL query. State-changing requests also require exact Origin and JSON; logout additionally checks a credential-bound CSRF value from authenticated status. There is no CORS allowance or arbitrary desktop command route.

Only approved profile metadata reaches status. Snapshot projection requires that exact profile to be active and unlocked; it never switches or unlocks a profile. One installation-wide job and the 30-second per-profile limit are admitted before queueing on the same worker used by desktop commands. Session revision/path generation and grants are checked before reads, after projection and at the first response-frame authorization check. Lock, switch or revoke before that delivery boundary discards unsent data. Bytes already handed to HTTP cannot be recalled. Profile deletion removes future grants; device or grant revocation does not erase phone-local offline copies.

`mobileConnection.ts` supplies bounded, timed browser API calls without storing credentials. Its refresh utility captures `prepareRefresh(binding)` before HTTP, passes that guard into replacement and obtains profile/epoch bindings from authenticated status; an epoch change requires explicit caller approval. Task 7 connects these utilities to the setup, QR/link, phone pairing, refresh and Forget flows below.

Compiled specs 167–170 cover confirmation/grants/real read-only projection/registry faults and deterministic queued/building/ready lock/switch/revoke races. Their debug actors use only disposable test directories and native runtime transitions. They do not prove physical phone trust, actual suspend/NIC changes or cross-browser cookie persistence.


## Setup and real refresh (Task 7)

Settings → Mobile snapshots provides opt-in private IPv4/interface and fixed-port setup, listener status, viewer address, server expiry, root fingerprint and public-only certificate export through the native Save dialog. Certificate files contain PEM without a CSV byte-order mark. The bundled SVG QR and manual link carry only a five-minute one-time pairing code in a fragment, which the phone removes from browser history on opening. The code can instead be pasted inside a home-screen shortcut so pairing uses that context’s storage. There is no external QR service or installer, no tray/autostart change and no firewall-wide action.

The setup instructions explain transferring and comparing the public root, iPhone/Android trust and removal, keeping a reserved address and checking private-network reachability. Trust is an owner action; certificate warnings must never be bypassed. Revoke and individual profile removal use the shared confirmation dialog. Device last-connection times are approximate, coalesced to five minutes. Explicit trust reset disables persisted access first, revokes every device, then replaces the protected root and installation identity. It remains stopped; the owner exports/trusts the new certificate and enables/pairs again. A new origin cannot inherit old browser snapshots.

The production viewer opens saved encrypted data immediately and makes one bounded selected-profile refresh on opening or returning to the foreground if this browser has remembered access. Manual Refresh and first Download use authenticated status bindings and a captured storage fence; no periodic away polling runs. Status supplies advisory readiness only for granted profiles. Initial download prefers an approved active/unlocked profile; selecting another profile never changes the desktop. Locked/inactive, unavailable, rate-limited, revoked, newer-viewer and storage states retain old copies and timestamps. A changed epoch requires explicit approval for that profile alone.

Phone approval polls only while an explicit pairing request is pending, for up to five minutes. Pairing completion saves only a non-secret remembered-access intent in IndexedDB; its fence prevents a pending approval restoring intent after Forget. Credentials remain in protected HTTP cookies, never URL query strings, localStorage, IndexedDB or Cache API. Forget removes encrypted rows, keys, pointer and remembered intent before contacting the desktop, then attempts authenticated logout/revocation and cookie expiry. Offline, a page cannot delete its HttpOnly cookie: the UI says to revoke on the desktop and disables automatic reconnection until explicit pairing. It retains no secret for deferred revocation. Clearing all browser site data also loses intent and requires pairing again.

Compiled spec 171 covers Settings/QR/grants/revoke/disable and six theme variants. Spec 172 uses production mobile assets and native Edge with an isolated loopback proxy to the actual compiled HTTPS projection; its Node client alone validates the fixture CA and holds the cookie. This establishes UI, first download, selected-profile isolation, inactive-profile retention, cached reopen and offline Forget. It does not validate browser TLS trust or Secure-cookie behavior. The physical and trusted-browser acceptance matrix remains Task 8, and macOS build/runtime acceptance remains unavailable on this Windows environment.


## Browser and physical acceptance (Task 8)

Install the pinned dev browser tooling with `npx playwright install chromium firefox webkit`. After the normal unit/lint/native gates and fresh debug Tauri build, `npm run mobile:acceptance:e2e` exercises three native engines against synthetic snapshots and the offline test entry. It checks real selections, five widths, all tabs/ranges, six theme variants, touch/keyboard, menu containment/focus, privacy, native encrypted storage and offline reload. This HTTP loopback run is UI/storage evidence, not TLS support.

`npm run mobile:tls:e2e` drives the packaged HTTPS viewer directly in Firefox on Windows. Its helper uses the copied browser's public NSS API to import a disposable root only into a checked temporary profile. It rejects untrusted roots and wrong hostname first, keeps certificate validation enabled, tests actual Secure/HttpOnly/Strict cookies and projection/encryption, and cold-restarts Firefox with the desktop stopped. It never calls Windows certificate installation or an ignore-HTTPS-errors option. Python and the existing compiled Tauri/init_db/WebDriver tools are required; Firefox and NSS profile handling here are Windows-specific.

Native WebKit exposed a shared menu focus issue: a pointer press could blur the menu and remove the selected option before click. MenuSelect now preserves focus through mousedown, with a failing-before/passing-after behavior test and real browser selection assertions. Automated Windows WebKit is not physical Safari/iOS; synthetic HTTP contexts are not the origin/certificate support matrix. The owner phone worksheet and launcher live outside the repository under `E:\misc\Programming\Claude\Implementations`; both iPhone and Android tests, home-screen contexts, long-term storage, real renewal/removal, actual network/power and macOS packaging/Keychain remain acceptance gates.

## Guided fully local setup (2026-10-05)

Settings > Mobile snapshots > Set up a phone opens the desktop guide. Explicit enablement migrates to an installation-bound `vault-spend-<opaque installation id>.local` hostname with a DNS SAN under the existing protected root. A changed private address on the same selected interface retains the name/root/origin; an app-owned monitor reconciles it. Ambiguous interfaces, discovery failures/conflicts and identity errors require attention. No public domain, DNS service, tunnel or financial relay. `mdns-sd` 0.21.5 (Apache-2.0 OR MIT) is scoped to the selected interface and shut down with the HTTPS listener. Physical router/browser support remains pending.

A separate opt-in ten-minute HTTP bootstrap on a private interface/ephemeral port serves only static phone instructions and the public certificate (`.crt`) or certificate-only iPhone `.mobileconfig`. Routes are exact, bounded and no-store; no API/IPC, pairing secret or private key is exposed. Cancel, disable, settings exit, interface loss, expiry and Quit stop it. Untrusted HTTP download is not identity proof: the guide requires verification of the actual downloaded certificate against the desktop or a trusted direct transfer. Where phone fingerprint inspection is unavailable, direct transfer is the explicit fallback; do not claim verification from a label or fingerprint printed on the bootstrap page.

The phone installs/trusts the certificate in Settings and opens the HTTPS viewer without a warning. Pairing uses a fresh trusted HTTPS QR/code and existing desktop profile approval. A home-screen context may need its own pairing/storage. Actual phone TLS/offline/readiness remains an acceptance gate, not established by the instruction UI. Existing IP-origin storage/cookies do not migrate automatically: guide requires acknowledgement, re-pair and a new snapshot; old copies stay at their old origin. Advanced IP controls and public certificate export remain available. Reset trust is explicit and revokes devices as before.

`feature173_mobile_guided_setup.mjs` drives compiled desktop opt-in/guide themes and a release-excluded, disposable, loopback-only bootstrap fixture; Chromium/Firefox/WebKit exercise actual phone-page routes and instruction controls. It does not enable LAN access or install any CA. Native tests cover DNS SAN/Host validation, same-root DHCP migration, corrupted identity, public profile DER contents, exact HTTP routes and cancellation.
